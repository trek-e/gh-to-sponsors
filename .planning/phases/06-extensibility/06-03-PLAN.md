Create ExamplePlugin implementing PlatformPlugin interface. Use an "Example Platform" that demonstrates all required patterns:
- `readonly name = 'example'`
- Constructor takes apiKey (string | undefined) and defaultTag (string, optional, defaults to 'devlog')
- `isConfigured()` returns Boolean(this.apiKey)
- Private `getClient()` with lazy initialization pattern - creates a simple mock-like client object (since this is a template, the "API client" is a placeholder showing where real SDK calls go)
- `async post(state: PostState)` with:
  - Content validation: return error if no digest
  - Configuration validation: return error if not configured
  - Lazy client usage
  - Try/catch wrapping the "API call" (in the example, just format the data to show what would be sent)
  - Never-throw: catch errors and return { success: false, error: message }
  - Retry logic with exponential backoff for 429 errors (MAX_RETRIES=3)
- Add JSDoc comments on every method explaining the pattern

Include inline comments marked with "// CUSTOMIZE:" at points where plugin authors need to make changes (e.g., "// CUSTOMIZE: Replace with your platform's SDK", "// CUSTOMIZE: Add your API-specific parameters").

**docs/plugins/community-submission.md** - "Contributing a Plugin"

Structure:
1. **Overview** - How the community plugin ecosystem works: authors publish npm packages, optionally register in community-plugins.json for discovery
2. **Step 1: Create Your Plugin** - Link to tutorial, use the example template as starting point
3. **Step 2: Ensure Quality** - Required: implements PlatformPlugin interface, all compliance tests pass (testPlatformPluginCompliance), has README with usage instructions, handles errors with never-throw pattern. Recommended: retry logic for rate-limited APIs, JSDoc on public methods.
4. **Step 3: Publish to npm** - Package naming convention: `@username/gh-to-sponsors-plugin-platformname`. Required keywords in package.json: "gh-to-sponsors", "plugin", "platform-name". Set type: "module" and provide TypeScript declarations.
5. **Step 4: Register in Community Directory (Optional)** - Submit PR to main repo adding entry to docs/community-plugins.json. Show exact JSON format for entry. Explain what maintainer reviews: npm package exists, tests pass, README exists.
6. **Self-Hosted Option** - Not required to register. Publish to npm with correct keywords and users can discover via npm search for "gh-to-sponsors plugin".
7. **Plugin Entry Schema** - Document the exact JSON schema for community-plugins.json entries: name (string, npm package name), description (string, what platform), author (string, GitHub username), repository (string, GitHub URL), npmPackage (string, npm URL).

Keep the process lightweight. This is a solo-developer project - no complex CI validation workflows or governance. The registry is a simple JSON file maintained via PRs.
