**docs/plugins/explanation-architecture.md** - "Plugin Architecture: Why Things Work This Way"

Structure:
1. **The Plugin Contract** - PlatformPlugin is intentionally minimal (3 members). Why: low barrier to entry, easy to implement, easy to test. Compare to over-engineered plugin interfaces with lifecycle hooks, config schemas, etc.
2. **Never-Throw Pattern** - Why post() returns PostResult instead of throwing. The executor uses Promise.allSettled for error isolation. If one plugin throws and it escapes the try/catch wrapper, it could crash the entire posting flow. PostResult { success: false, error } is the contract.
3. **Lazy Initialization** - Why plugins don't create API clients in the constructor. The registry creates ALL plugins on every run (getConfiguredPlatforms calls every factory). If constructors made API connections, unconfigured platforms would fail loudly. Lazy init via getClient() defers until post() is called.
4. **Factory Registration** - Why factories instead of instances. The registry stores functions, not objects. This allows: lazy instantiation, fresh credentials on each invocation, no stale state between runs. Show registerPlatform pattern.
5. **Error Isolation with Promise.allSettled** - How the executor ensures Ghost failing doesn't prevent Bluesky from posting. Show the executor flow: Ghost first (for URL), then social platforms in parallel via Promise.allSettled.
6. **Retry with Exponential Backoff** - Why jitter matters (thundering herd), why MAX_RETRIES=3 (1s + 2s + 4s = 7s max wait), why only retry 429 (other errors are permanent).
7. **Content Flow** - How PostState flows: digest for long-form platforms (Ghost), teaser for social platforms (Bluesky, Mastodon). The executor composes teaser + link for social. Explain what content each plugin type should use.

Use actual code snippets from the existing plugins to illustrate each concept. Reference specific files (e.g., "See src/platforms/executor.ts line X").
